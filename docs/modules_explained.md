# Как и почему работают драйверы и модули

Документ описывает текущую реализацию проекта `lab1`. Его можно использовать при чтении кода и подготовке к защите. Сначала рассмотрен поток выполнения, затем каждый модуль и его ограничения.

## 1. Общая организация

```text
main
 ├─ HAL_Init → SystemClock_Config
 ├─ Led_Init → Gpio_EnableClock, Gpio_Configure
 ├─ Button_Init → Gpio_EnableClock, Gpio_Configure
 ├─ MorseApp_Init
 └─ бесконечный цикл
     ├─ HAL_GetTick
     ├─ Button_Update → Gpio_Read
     └─ MorseApp_Update → события кнопки и команды Led

SysTick_Handler → HAL_IncTick → значение HAL_GetTick
```

Разделение необходимо, чтобы алгоритм Морзе не зависел от конкретных GPIO. Приложение знает, какой символ передать, LED-драйвер знает, какой контакт включает цвет, а GPIO-драйвер знает, в какой регистр записать бит. Аналогично кнопка преобразует электрический уровень в устойчивое состояние и события, а приложение решает, что означает длительность нажатия.

## 2. GPIO-драйвер — `gpio.h` и `gpio.c`

### 2.1. Назначение типов

`GpioConfig` содержит пять независимых параметров: `mode`, `output_type`, `pull`, `speed`, `alternate`. Численные значения перечислений соответствуют значениям аппаратных полей. Например, режимы 0, 1, 2 и 3 означают вход, выход, альтернативную функцию и аналоговый режим.

Макрос `GPIO_DRIVER_PIN(n)` строит маску одного контакта: для PD13 она равна `1 << 13`, то есть `0x2000`. Номер контакта и маска различаются: одиночные функции принимают номер 0–15, групповые — маску. Макрос предполагает допустимый номер; проверка в самом макросе не выполняется.

`GPIO_TypeDef` предоставляет имена регистров и их адреса. Использование этого описания не вызывает стандартные функции GPIO. Регистры имеют квалификатор `volatile`, поэтому компилятор не может произвольно удалить обращения к аппаратуре.

### 2.2. `Gpio_PortIndex`

Внутренняя функция сравнивает переданный указатель с адресами GPIOA–GPIOK. Возвращаемый индекс используется как номер бита в AHB1ENR. Если адрес не соответствует известному порту, возвращается −1. Это защищает функции включения тактирования и настройки от неправильного указателя.

### 2.3. `Gpio_EnableClock`

До обращения к периферии необходимо включить её тактирование. Функция устанавливает соответствующий бит RCC AHB1ENR, сохраняя остальные биты. После записи выполняется чтение регистра обратно — это обеспечивает предусмотренный для включения периферии промежуток до следующих обращений. Тактирование не выключается и состояние порта не сбрасывается.

Возвращаемое `false` означает неизвестный порт. Перед использованием остальных функций тактирование должен включить вызывающий код: `Gpio_Configure` этого автоматически не делает.

### 2.4. `Gpio_Configure`

Функция принимает порт, маску контактов, одинаковую для выбранной группы конфигурацию и начальные значения выходов. Если разные контакты требуют разных режимов, функцию вызывают для отдельных масок.

Алгоритм состоит из следующих шагов:

1. Проверить порт, непустую маску, указатель на конфигурацию и допустимость всех полей.
2. Проверить LCKR. При активном бите блокировки и наличии выбранных заблокированных контактов отклонить всю операцию.
3. Для каждого выбранного контакта собрать маски двухбитных полей MODER, PUPDR и OSPEEDR, однобитного OTYPER и четырёхбитного AFR.
4. Если контакт обслуживается AF либо требуется изменить режим или тип работающего GPIO-выхода, предварительно перевести его во вход.
5. Для нового режима output записать требуемую выходную защёлку через BSRR.
6. Записать OTYPER, OSPEEDR, PUPDR и AFR.
7. Последним записать окончательный MODER.

Для контакта `n` двухбитное поле находится со сдвигом `2*n`. AFR имеет два регистра: индекс `n/8`, сдвиг `4*(n%8)`. Поэтому алгоритм одинаков для всех 16 контактов.

Выражение `(register & ~mask) | value` сначала очищает только выбранные поля, затем устанавливает новые значения. Простое `register |= value` было бы неправильным: оно не позволяет убрать прежние единицы при повторной настройке.

Начальный ODR подготавливается до подключения выхода. Иначе выход мог бы на короткое время выдать прежнее значение защёлки. Если режим и тип уже работающего выхода совместимы с новой конфигурацией, драйвер не отключает его; `output_values` при этом задаёт желаемое новое состояние.

Переход через вход временно отключает активный выходной драйвер. Это устраняет неправильное активное управление во время настройки, но создаёт высокий импеданс. Внешняя схема может изменить уровень ножки в этот момент. Поэтому нельзя обещать отсутствие любых электрических импульсов для произвольной нагрузки только на основании кода. Для критичных сигналов нужны подходящие подтяжки, согласованная процедура переключения и проверка осциллографом.

### 2.5. `Gpio_GetConfig`

Функция читает регистры, сдвигает поле нужного контакта к младшим битам и выделяет его маской. Например, `(MODER >> (2*n)) & 3` возвращает режим. Полученная конфигурация отражает аппаратные регистры, а не сохранённую копию последнего вызова настройки.

Проверяются адрес порта, номер контакта и указатель результата. Сам драйвер не исправляет зарезервированное значение подтяжки 3, если оно оказалось в регистре: чтение показывает фактические биты.

### 2.6. Чтение: `Gpio_Read`, `Gpio_ReadPin`, `Gpio_ReadOutput`

`Gpio_Read` возвращает `IDR & pins`. Результат остаётся в исходных позициях битов: прочитанная единица PD13 имеет значение `0x2000`, а не 1. `Gpio_ReadPin` преобразует результат для одного контакта в `bool`.

`Gpio_ReadOutput` читает ODR — сохранённую команду выходу. IDR показывает наблюдаемый цифровой уровень. Эти значения могут различаться, например при open-drain: в ODR находится 1, выход отпущен, но внешняя цепь удерживает ножку в нуле. Состояние аналогового входа нельзя интерпретировать как обычное корректное цифровое чтение IDR.

### 2.7. Запись: `Gpio_Write`, `Gpio_WritePin`

`Gpio_Write` формирует непересекающиеся маски установки и сброса и записывает их в BSRR. Младшие 16 бит устанавливают единицы, старшие 16 сбрасывают соответствующие выходы. Нули BSRR не изменяют состояние контактов.

Пример: `Gpio_Write(GPIOD, 0xC000, 0x8000)` одновременно устанавливает PD15 и сбрасывает PD14, включая красный цвет. PD13 и остальные контакты сохраняются.

`Gpio_WritePin` строит одиночную маску и вызывает групповую запись. Недопустимый номер контакта не приводит к записи. Групповые функции чтения и записи предполагают корректный указатель порта; полной проверки всех аргументов в них нет. В текущих драйверах передаются фиксированные допустимые адреса.

BSRR позволяет выполнить атомарную запись выбранных выходов. Это не делает атомарной всю многошаговую настройку: операции изменения конфигурации рассчитаны на последовательные вызовы в главном цикле, без конкурентной работы прерываний.

## 3. LED-драйвер — `led.h` и `led.c`

Драйвер содержит привязку зелёного LED к PD13, жёлтого направления двухцветного LED к PD14 и красного к PD15. Приложение передаёт логические команды, не вычисляя маски регистров.

`Led_Init` включает тактирование GPIOD и задаёт для трёх контактов push-pull, отсутствие подтяжки и минимальную скорость. Начальные уровни нулевые. Низкая скорость означает ограничение скорости фронтов, а не редкое включение LED: для человеческой индикации быстрые фронты не требуются.

`Led_Set` проверяет идентификатор LED, сохраняет его логическое состояние в `green_is_on` и записывает PD13. `Led_On` и `Led_Off` — короткие обёртки. `Led_Toggle` инвертирует сохранённое состояние. Если PD13 изменён извне напрямую через GPIO или отладчик, эта копия может стать неактуальной; приложение должно управлять зелёным LED через данный драйвер.

`Led_SetBicolor` выбирает одну из трёх масок: красный, жёлтый или выключено. Оба контакта меняются одной записью. Для неизвестного значения перечисления используется выключенное состояние.

Ни одна функция LED не определяет длительность свечения. Это делает драйвер пригодным и для Морзе, и для тестового приложения. Все паузы остаются на прикладном уровне.

## 4. Драйвер кнопки — `button.h` и `button.c`

### 4.1. Инициализация и активный уровень

`Button_Init` включает тактирование GPIOC и настраивает PC15 как вход без внутренней подтяжки. `Button_ReadRaw` возвращает `true`, когда IDR выбранного контакта равен нулю: электрически кнопка активна низким уровнем.

Начальное состояние принимается сразу при инициализации, события очищаются. Это означает, что удерживаемая при запуске кнопка считается нажатой без предварительного 30-миллисекундного ожидания.

### 4.2. Состояния фильтра

| Переменная | Смысл |
|---|---|
| `stable_pressed` | Последнее принятое устойчивое состояние |
| `candidate_pressed` | Состояние, устойчивость которого сейчас проверяется |
| `candidate_since_ms` | Начало наблюдения текущего кандидата |
| `pressed_event` | Непрочитанное событие нажатия |
| `released_event` | Непрочитанное событие отпускания |

При изменении сырого уровня кандидат заменяется, а его время отсчитывается заново. Если состояние сохраняется не менее 30 мс и отличается от стабильного, принимается переход. Например, несколько чередований 0/1 в течение первых 12 мс не создадут события: каждое изменение заново запускает проверку устойчивости.

Драйвер фиксирует устойчивость только по наблюдениям. Очень короткие изменения между опросами он не видит, поэтому `Button_Update` нужно вызывать часто. В текущем главном цикле блокирующих действий нет.

### 4.3. События и время

`Button_IsPressed` не изменяет состояние. `Button_WasPressed` и `Button_WasReleased` возвращают соответствующий флаг и очищают его. Повторное чтение без нового события возвращает `false`.

Флаги не являются очередью: несколько одинаковых событий между чтениями объединяются в одно. В текущем приложении события читаются на каждом проходе цикла.

Проверка времени использует беззнаковую разность `now - candidate_since_ms`. Она корректно переживает переполнение миллисекундного счётчика для коротких интервалов. Стабильное событие приходит приблизительно через 30 мс после последнего наблюдаемого изменения, с дополнительной погрешностью порядка периода опроса.

## 5. Модуль Морзе — `morse_app.h` и `morse_app.c`

### 5.1. Почему используется конечный автомат

Во время ожидания конца импульса требуется продолжать опрашивать кнопку. Поэтому передача разбита на состояния и каждый вызов `MorseApp_Update` выполняет только один небольшой шаг. Состояние автомата хранит, что программа делает сейчас, а дедлайн — когда можно перейти дальше.

`MorseApp_Init` очищает буфер, выбирает `INPUT`, выключает LED и учитывает кнопку, уже удерживаемую при запуске. Буфер `sequence` имеет статический размер 32 элемента; динамическая память не используется.

### 5.2. `MorseApp_HandleInput`

При событии нажатия сохраняется время начала и выключается прежнее цветовое подтверждение. При отпускании вычисляется длительность между стабильными событиями. До 500 мс выбирается точка, начиная с 500 мс — тире. Если в буфере есть место, символ записывается и включается цветовое подтверждение на 180 мс.

Затем функция независимо проверяет окончание подтверждения и тайм-аут ввода. Передача начинается только при непустом буфере, отсутствии текущего удержания и истечении 1500 мс после последнего отпускания. Продолжительное удержание не запускает передачу ранее завершённой последовательности.

Длительность измеряется по событиям после фильтра дребезга. Задержки принятия нажатия и отпускания примерно компенсируются, но их различия и период опроса дают небольшую погрешность у порога 500 мс.

### 5.3. Передача и переходы

| Состояние | Действие | Переход |
|---|---|---|
| `INPUT` | Собирать символы и проверять тайм-аут | Начало передачи → `TRANSMIT_ON` |
| `TRANSMIT_ON` | Зелёный LED включён до дедлайна | Выключить LED, увеличить индекс → `TRANSMIT_GAP` |
| `TRANSMIT_GAP` | Выдержать паузу 250 мс | Следующий символ → `TRANSMIT_ON`; конец → `INPUT` |

`MorseApp_StartTransmission` выключает цветовое подтверждение, выбирает первый символ и включает зелёный LED. Вызов безопасен, поскольку перед ним проверяется непустой буфер.

`MorseApp_SymbolDuration` возвращает 250 мс для точки и 750 мс для тире. `MorseApp_FinishTransmission` очищает длину и индекс и возвращает ввод. Перед возвратом после последнего символа также выдерживается пауза 250 мс.

Во время передачи события кнопки очищаются и не добавляют символы. Если кнопку нажать во время передачи и продолжить держать при возврате к вводу, её прежнее событие нажатия уже потеряно; для нового символа потребуется новое полноценное нажатие. Это ограничение текущего алгоритма.

### 5.4. Дедлайны и точность

`MorseApp_DeadlineReached` проверяет `(int32_t)(now - deadline) >= 0`. Для используемых коротких интервалов это позволяет корректно сравнивать время через переполнение счётчика. Предполагается, что проверки не пропускаются на интервалы порядка половины диапазона 32-битного счётчика.

Следующий дедлайн вычисляется от фактического текущего времени, поэтому при задержке главного цикла этап немного удлиняется. Автомат не пытается мгновенно выполнить все пропущенные этапы. В нормальном цикле длительность операций намного меньше интервалов 180–1500 мс.

## 6. Тест LED — `led_test_app.h` и `led_test_app.c`

Модуль позволяет проверить аппаратные уровни отдельно от Морзе. Цикл длится четыре секунды: зелёный 500 мс, красный 500 мс, жёлтый 500 мс, всё выключено 500 мс, затем зелёный повторяет стабильное состояние кнопки 2000 мс.

`LedTestApp_Init` задаёт первую фазу. `LedTestApp_ApplyPhase` сначала выключает индикацию, затем задаёт нужный цвет или состояние кнопки. `LedTestApp_Update` читает события кнопки и проверяет время фазы. После истечения интервала номер фазы увеличивается по модулю числа фаз.

При входе в фазу кнопки считывается её текущее состояние, поэтому LED правильно включится даже для нажатия, начавшегося в предыдущей фазе. Паузы реализованы без задержек, а кнопка обслуживается главным циклом во всех фазах.

## 7. Платформа — `system_clock.h`, `system_clock.c`, `stm32f4xx_it.c`

`SystemClock_Config` задаёт источник HSE 25 МГц и PLL: M = 25, N = 360, P = 2. Расчёт SYSCLK: `25 МГц / 25 × 360 / 2 = 180 МГц`. AHB работает на 180 МГц, APB1 на 45 МГц, APB2 на 90 МГц.

Перед включением режима 180 МГц выбираются Voltage Scale 1, OverDrive и пять тактов ожидания Flash. Это необходимо, чтобы ядро и память работали при предусмотренных настройках питания и частоты. Значение HSE контролируется директивой препроцессора: при другом `HSE_VALUE` сборка останавливается.

PLLQ = 8 даёт выход 45 МГц от VCO 360 МГц. Он не является корректным источником 48 МГц для USB; текущая программа USB-периферию микроконтроллера не использует, а FTDI — отдельное устройство стенда.

`SysTick_Handler` вызывает `HAL_IncTick`, увеличивая счётчик времени. `HAL_GetTick` читает этот счётчик. SysTick — разрешённое заданием исключение; прерывания от кнопки и дополнительные аппаратные таймеры не применяются.

## 8. Точки входа `main.c`

Оба основных приложения сначала вызывают `HAL_Init`, затем настраивают частоты, инициализируют LED и кнопку, после чего соответствующий прикладной модуль. При ошибке настройки частот вызывается `NVIC_SystemReset`; код не предоставляет пользователю отдельную диагностику этой ошибки и может повторять перезапуск.

В цикле один раз получается текущее время, затем обновляется кнопка и приложение. Функции драйверов LED и кнопки игнорируют результат настройки GPIO, поскольку используют заранее известные допустимые порты и параметры. Если вне программы заблокировать эти контакты через LCKR, отдельной обработки такой ошибки здесь нет.

## 9. Аппаратный самотест — `src/apps/gpio_selftest/main.c`

Самотест использует только PD13–PD15, предназначенные для LED. Перед испытанием сохраняются поля остальных контактов GPIOD. Затем проверяются групповые и одиночные записи, чтение IDR и ODR, повторная настройка, input/output/analog, типы выхода, подтяжки, скорости, чтение AFR и отклонение неверных параметров.

AFR проверяется при входном режиме: самотест не подключает неизвестную периферию к LED. Настоящее аппаратное запирание LCKR не выполняется, чтобы не блокировать последующую работу до сброса. Работа с установленной блокировкой проверяется тестом на компьютере.

`Check` увеличивает число проверок и, если условие ложно, число ошибок. По завершении устанавливается `gpio_test_done = 1`, затем запускается обычный четырёхсекундный тест LED. Результаты можно прочитать по именам символов через JTAG.

Прошивка собрана, но её выполнение на стенде пока не подтверждено: загрузку блокирует USB-драйвер Interface A.

## 10. Тест на компьютере — `test/gpio_host/`

Тестовый `stm32f4xx.h` определяет структуры регистров и фиктивные адреса GPIOA–GPIOK. Благодаря порядку include-путей настоящий `gpio.c` собирается с этими структурами вместо аппаратного описания. Алгоритм драйвера не копируется в отдельную реализацию.

`main.c` проверяет 16 контактов × 4 режима × 3 подтяжки × 2 типа выхода, то есть 384 комбинации. До каждой проверки регистры заполняются шаблоном, чтобы обнаружить случайную порчу соседних полей. Дополнительно перебираются все 65 536 значения `values` для маски `0xA55A`; проверяется правильность половин BSRR и отсутствие пересечения установки со сбросом.

Также проверяются включение тактирования, цифровое чтение, неверные аргументы и отказ при LCKR без изменения регистров. Все эти тесты прошли.

Фиктивный BSRR сохраняет записанное значение, но автоматически не меняет ODR и не моделирует электрический сигнал. Поэтому эти тесты не подтверждают реальные фронты, напряжения, дребезг или аппаратный эффект BSRR. Они дополняют аппаратный самотест.

## 11. Конфигурация сборки и загрузки

`platformio.ini` выбирает платформу, STM32Cube, плату и JTAG-инструмент. Среда по умолчанию — `sdk11m_lab1_v3`. Три среды имеют отдельные фильтры исходников; для самотеста дополнительно подключается модуль теста LED, но исключается его `main.c`.

`boards/sdk11m_427.json` описывает STM32F427VIT6, частоту 180 МГц, объёмы Flash/RAM и способ запуска OpenOCD. Описание платы направляет сборку и выбирает подходящую карту памяти; оно само не настраивает GPIO или частоты работающего микроконтроллера.

`openocd/sdk11m_427.cfg` задаёт FTDI `0403:6010`, JTAG, частоту адаптера 1 МГц, линии сброса и стандартный target STM32F4. Выборка TDO по спадающему фронту сохранена из ранее подобранной конфигурации стенда.

При текущем подключении оба интерфейса используют FTDI-драйвер. Для данного OpenOCD Interface A (`MI_00`) должен использовать WinUSB, Interface B (`MI_01`) остаётся FTDI. До исправления этого условия новые прошивки не загружены.

## 12. Краткие ответы для защиты

**Почему нельзя поставить задержку после нажатия?** Она остановит обслуживание передачи и прочих процессов. Здесь дребезг фильтруется сравнением времени при каждом опросе.

**Почему GPIO, LED и кнопка — разные драйверы?** GPIO решает универсальную задачу работы с портом, а LED и кнопка описывают конкретные устройства стенда. При изменении алгоритма Морзе они не меняются.

**Чем BSRR лучше записи ODR через read-modify-write?** Он меняет выбранные выходы одной записью без чтения старого ODR. Установка и сброс группы выполняются согласованно, а невыбранные биты сохраняются.

**Почему начальное значение записывается до MODER?** После подключения выход выдаёт уже подготовленный уровень, а не старое содержимое защёлки.

**Почему недостаточно операции OR при настройке?** Она не очищает старые единицы. Повторная настройка требует очистить целевое поле и затем записать новое значение.

**Почему осталось использование HAL?** Задание способа 1 запрещает стандартное управление GPIO. HAL для тактирования, SysTick и запуска системы оставлен; GPIO управляется собственным кодом.

**Чем эта реализация отличается от LL?** Оба подхода работают с регистрами, но здесь собственные типы, API, алгоритм групповой настройки, подготовка уровня и проверка блокировки. Вызовов LL нет.

**Можно ли считать часть 2 симуляцией?** Нет: выбран способ 1, код предназначен для микроконтроллера. Тестовые структуры на компьютере используются только для проверки этого драйвера.

**Подтверждено ли отсутствие любых выбросов на выводах?** Код задаёт последовательность, исключающую подключение старого активного уровня. Полное электрическое подтверждение, особенно при переходе через высокий импеданс, требует измерений и пока не выполнено.
