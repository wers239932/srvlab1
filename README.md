# SDK-1.1M.427 — лабораторная работа №1, вариант 3

Проект PlatformIO предназначен для процессорного модуля SDK-1.1M `.427` на
STM32F427VIT6. Часть 2 выполнена способом 1: собственный регистровый GPIO-драйвер.
STM32Cube HAL сохранён для системной инициализации, тактирования и SysTick;
для GPIO он не используется. Блокирующих задержек и динамической памяти нет.

В проекте сохранены три независимо собираемых приложения:

- `sdk11m_led_test` — проверка светодиодов и кнопки;
- `sdk11m_lab1_v3` — передатчик последовательности точек и тире.
- `sdk11m_gpio_selftest` — проверки GPIO на стенде, затем тест LED/кнопки.

Все приложения используют общие драйверы GPIO, LED, кнопки, настройку тактирования и
обработчик системного таймера.

## Что было сделано

1. Вместо временно выбранной платы `armstrap_eagle2048` создано локальное
   описание `boards/sdk11m_427.json` для STM32F427VIT6: Cortex-M4, 2 МБ Flash,
   256 КБ суммарной RAM и частота ядра 180 МГц. Используется штатный linker
   script PlatformIO для STM32F427VIT6; самодельная карта памяти не создавалась.
2. Настроено тактирование от HSE 25 МГц: PLLM=25, PLLN=360, PLLP=2,
   SYSCLK/HCLK=180 МГц, PCLK1=45 МГц и PCLK2=90 МГц. Для 180 МГц включены
   Voltage Scale 1, OverDrive и Flash latency 5.
3. Добавлена конфигурация встроенного FTDI JTAG-программатора SDK-1.1M для
   OpenOCD 0.12.x. На этом экземпляре стенда для устойчивого DAP-доступа
   потребовалась выборка TDO по спадающему фронту (`ftdi tdo_sample_edge
   falling`).
4. Реализован общий неблокирующий LED-драйвер. Он скрывает PD13, PD14, PD15,
   активные уровни и управление двухцветным светодиодом.
5. Реализован общий драйвер кнопки PC15 с активным низким уровнем и
   неблокирующим debounce 30 мс. Внутренняя подтяжка не включается, поскольку на
   плате есть внешняя подтяжка 3 кОм.
6. Добавлен `SysTick_Handler`, вызывающий `HAL_IncTick()`. Без него обработчик
   первого системного тика попадал в `Default_Handler`, и логика по
   `HAL_GetTick()` останавливалась.
7. Реализованы отдельное тестовое приложение и конечный автомат лабораторной
   работы. Детали GPIO отсутствуют в прикладном коде и `main.c`.

## Подключение и загрузка

Загрузка и отладка выполняются через разъём DBG USB и встроенный FTDI с
VID:PID `0403:6010`.

В Windows только `Dual RS232 (Interface 0)` / Interface A (`MI_00`) должен
использовать WinUSB. Interface B (`MI_01`) должен оставаться на штатном драйвере
FTDI. Выбирать в Zadig устройства без проверки VID, PID и MI нельзя.

```text
pio run -e sdk11m_led_test
pio run -e sdk11m_lab1_v3
pio run -e sdk11m_led_test -t upload
pio run -e sdk11m_lab1_v3 -t upload
```

## Тест светодиодов и кнопки

Тест повторяет четырёхсекундный цикл:

| Время цикла | Зелёный LED | Двухцветный LED |
|---|---|---|
| 0–500 мс | включён | выключен |
| 500–1000 мс | выключен | красный |
| 1000–1500 мс | выключен | жёлтый |
| 1500–2000 мс | выключен | выключен |
| 2000–4000 мс | повторяет состояние кнопки | выключен |

На физическом стенде подтверждены все цвета и реакция кнопки. Дополнительно
через JTAG были проверены соответствующие значения GPIOD ODR: `0x2000`,
`0x8000`, `0x4000`, `0x0000`.

## Лабораторная работа: передатчик Морзе

В режиме ввода длительность каждого стабильного нажатия измеряется между
событиями press/release:

- нажатие короче 500 мс сохраняется как точка и подтверждается жёлтой вспышкой
  длительностью 180 мс;
- нажатие от 500 мс сохраняется как тире и подтверждается красной вспышкой
  длительностью 180 мс;
- после 1500 мс без нового завершённого нажатия начинается передача.

Передача выполняется зелёным светодиодом: точка горит 250 мс, тире — 750 мс,
пауза между символами — 250 мс. После последнего символа буфер очищается, и
приложение возвращается к вводу новой последовательности.

Конечный автомат имеет состояния `INPUT`, `TRANSMIT_ON` и `TRANSMIT_GAP`.
Каждый вызов `MorseApp_Update()` только проверяет события и дедлайны, поэтому
кнопка продолжает обслуживаться без `HAL_Delay()` и busy wait.

Последовательность хранится в статическом массиве на 32 символа. После его
заполнения новые символы игнорируются до передачи текущей последовательности;
выхода за границы массива нет.

## Часть 2, способ 1: собственный GPIO

API находится в `include/drivers/gpio.h`, реализация — в `src/drivers/gpio.c`.
Драйвер использует CMSIS-описание регистров `GPIO_TypeDef`, собственные
перечисления и структуру `GpioConfig`. Функций и структур HAL/LL для GPIO нет.
В проекте нет файла `.ioc`: ножки настраиваются только собственным драйвером.
Приложение по умолчанию теперь `sdk11m_lab1_v3`.

| Функция | Назначение и регистры |
|---|---|
| `Gpio_EnableClock` | Включение порта A–K через RCC AHB1ENR и чтение обратно |
| `Gpio_Configure` | Групповая настройка MODER, OTYPER, OSPEEDR, PUPDR, AFR |
| `Gpio_GetConfig` | Чтение текущей аппаратной конфигурации одного пина |
| `Gpio_Read`, `Gpio_ReadPin` | Чтение группы входов или одного входа через IDR |
| `Gpio_ReadOutput` | Чтение выходной защёлки ODR, отличной от физического IDR |
| `Gpio_Write`, `Gpio_WritePin` | Запись группы выходов или одного выхода через BSRR |

Номера пинов для одиночных функций — 0–15; групповые функции принимают
16-битную маску. В `Gpio_Write(port, pins, values)` единицы `values` задают
высокий уровень только внутри `pins`; остальные выбранные выходы сбрасываются.
BSRR записывается одной операцией: младшие 16 бит устанавливают выходы,
старшие сбрасывают. Поэтому красный/жёлтый LED переключается одновременно
по двум ножкам без промежуточной записи «выключить всё».

### Повторная настройка и отсутствие ошибочного активного уровня

Битовые поля заменяются целиком с сохранением соседних пинов. Повторная
настройка может уменьшать значения полей, а не только добавлять единицы.
До изменения регистров проверяются параметры и аппаратная блокировка LCKR.
Если выбран хотя бы один заблокированный пин, вся настройка отклоняется.

При переходе в GPIO output нужное значение записывается в BSRR до включения
выходного драйвера через MODER. При повторной настройке совместимого выхода
он остаётся подключённым; переданный `output_values` задаёт его желаемый уровень.
При смене типа активного выхода или выходе из AF драйвер сначала переводит
соответствующие пины во входной режим, затем настраивает управляющие поля и
в последнюю очередь включает новый режим. Таким образом не подключается
выход с устаревшим ODR или промежуточной конфигурацией.

При смене push-pull/open-drain или AF возможен короткий участок высокого
импеданса. Уровень физической ножки в это время определяется внешней схемой
и подтяжкой; программный порядок записей сам по себе не гарантирует уровень
на произвольной нагрузке. Для строгой проверки отсутствия электрических
импульсов нужен осциллограф. Самотест и чтение регистров этого не доказывают.
Для используемых LED push-pull сохраняется, начальный уровень — выключено;
у кнопки остаётся вход с внешней подтяжкой.

### Отличия от HAL и LL для защиты

- Собственная структура описывает режим, тип выхода, скорость, подтяжку и AF
  раздельно, непосредственно по полям регистров; EXTI не поддерживается.
- Настройка группы использует маски и замену полей, включает подготовку ODR
  и последовательность переключения режима. Проверка LCKR возвращает ошибку
  до любых изменений, а `Gpio_GetConfig` читает аппаратные настройки.
- В сравнении с HAL отсутствуют HAL GPIO API и `GPIO_InitTypeDef`; в сравнении
  с LL отсутствуют LL GPIO API и структуры. Сам принцип прямого доступа
  к регистрам похож на LL, но алгоритм и интерфейс написаны в этом проекте.
- Универсальный GPIO-драйвер ничего не знает о Морзе, LED и кнопке. Их
  назначение и активные уровни остаются в отдельных драйверах части 1.

Вызовы сериализуются главным циклом. Групповая запись BSRR атомарна;
операции read-modify-write настроек не рассчитаны на параллельные вызовы из
прерываний. Это соответствует запрету GPIO-прерываний в задании.
Источник описания регистров:
[ST RM0090, глава General-purpose I/Os](https://www.st.com/resource/en/reference_manual/rm0090-stm32f405415-stm32f407417-stm32f427437-and-stm32f429439-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).

### Результаты проверки изменений 05.10.2026

Все три приложения собираются успешно. В ELF варианта 3 нет символов
`HAL_GPIO`/`LL_GPIO`. На компьютере выполнены тесты настоящего исходника
`gpio.c` с подменённым описанием регистров: 384 комбинации конфигураций,
65 536 вариантов BSRR, чтение входов, отклонение заблокированных и неверных
настроек, сохранность соседних пинов. Это тесты программы, не симулятор части 2.

```powershell
gcc -std=c11 -Wall -Wextra -Werror -Itest/gpio_host -Iinclude src/drivers/gpio.c test/gpio_host/main.c -o .pio/gpio_host_test.exe
.pio/gpio_host_test.exe
pio run -e sdk11m_gpio_selftest -t upload
```

Аппаратный самотест сохраняет результаты в `gpio_test_checks`,
`gpio_test_failures` и `gpio_test_done`, доступные через JTAG. После его
прохождения следует загрузить `sdk11m_lab1_v3`.

На момент этой проверки загрузка не выполнена: OpenOCD сообщает
`LIBUSB_ERROR_NOT_FOUND`. Windows видит FTDI `0403:6010`, но Interface A
(`MI_00`, USB Serial Converter A) использует FTDI `oem90.inf`, а не WinUSB.
Для загрузки через данный OpenOCD следует назначить WinUSB только Interface A
через Zadig; Interface B (`MI_01`) оставить с FTDI. Драйверы в ходе работы
не менялись. Исторические результаты проверки старой HAL-прошивки выше
не являются результатами аппаратной проверки нового GPIO-драйвера.
